# Mastic on the Elpi grammar

This directory applies Mastic to a real language: the parser of
[Elpi](https://github.com/LPCIC/elpi). It shows, step by step, what has to be
added to a Menhir parser to make it error resilient, and it measures how good
the result is.

## 1. The problem

A compiler may stop at the first syntax error, an editor cannot: while
someone types, the program is almost never correct, yet the language server
must still highlight it, find definitions, complete names. It needs a parser
that **always returns a syntax tree**, where the broken parts are marked as
errors and the rest is as it would be without the error.

Take the clause

```prolog
p :- X is + 2 * 3.
```

The left operand of `+` is missing. A good error-resilient parser should
return the tree of `p :- X is Err + 2 * 3`: a hole `Err` where the operand
should be, and the rest, `+ 2 * 3`, parsed normally. That is what this
directory achieves:

```
$ echo 'p :- X is + 2 * 3.' | ./main.exe
input: p :- X is + 2 * 3.
error:           ^        recovered syntax error
error: line 1, column 10: completed with _
ast:
  clause (:- p (is X (+ Err«» (* 2 3))))
```

Mastic does the hard part: it drives the parser generated by Menhir, and
when a token does not fit, it repairs the parse. The grammar writer provides
three things, the three steps of the [README of Mastic](../README.md), which
are the sections 4 to 6 below.

In Elpi itself these changes do not touch the normal parsing path: the
error-resilient parser is a separate entry point. On 395 files (the
programs of Elpi's `tests/sources` and the corpus), the normal path gives
exactly the same declarations and errors as Elpi's master.

## 3. Trying it

```sh
dune build ./test_elpi/main.exe
echo 'p :- X is + 2 * 3.' | ./_build/default/test_elpi/main.exe   # one program
./_build/default/test_elpi/main.exe -ref good.elpi bad.elpi       # with the measure
dune runtest test_elpi                                            # the cram tests
python3 test_elpi/recov.py fuzz test_elpi/corpus/*/*.elpi         # the simulation
```

How to read the output of `main.exe`:

```
input: p 1.                             the program, line by line
       p $ 2.
error:   ^    recovered syntax error    under a line: the error nodes in it
       p 3.
error: unexpected character $ lexical error
ast:                                    the recovered AST, one declaration per line
  clause (p 1)                          terms are s-expressions: (f a b) is f a b
  clause (p Err«$» 2)                   an error node shows the text it covers
  clause (p 3)
```

When the recovery inserts a token, a line `error: line L, column C:
completed with T` says it; with `-ref` or `-fuzz`, a line `measure: …` gives
the measure of section 8.

## 4. Step 1: an error node in every AST type

The parser can only return a tree with errors if the tree can hold them. So
every type of the AST that can be broken gets a constructor for errors, which
carries a `Mastic.Error.t` (the pieces of text and subtrees that were folded
into the error, with their positions):

```ocaml
(* parser/ast.ml *)
module Term = struct
  type t_ =
   | Const of Func.t
   | App of t * t list
   ...
   | Err of Mastic.Error.t                     (* a broken term *)
  and t = { it : t_; loc : Loc.t }
end

module TypeExpression = struct
  type 'a t_ = TConst of Func.t | TArr of ... | ...
    | TErr of Mastic.Error.t                   (* a broken type *)
end

type raw_attribute = If of string | Name of string | ...
  | AttributeError of Mastic.Error.t           (* a broken attribute *)

module Program = struct
  type decl = Clause of ... | Pred of ... | Type of ... | ...
    | Error of Mastic.Error.t                  (* a broken declaration *)
end
```

Each error node is *registered* with Mastic, which tells Mastic how to build
it and how to recognise it. This is the boilerplate of the README of Mastic:

```ocaml
type Mastic.Error.t_ += Term of t              (* a term inside an error *)
let Mastic.Error.Registered { of_token; build_token; _ } =
  Mastic.Error.register "Term.t" {
    Mastic.Error.pp = pp;
    match_ast = (function { it = Err x } -> Some x | _ -> None);
    match_error = (function Term x -> Some x | _ -> None);
    build_ast = (fun x -> { it = Err x; loc = loc_of_error x });
    build_error = (fun x -> Term x) }
```

`of_token` turns an error token into an error node (used by the grammar,
step 2); `build_token` turns a correct term into a piece of an error (used
when Mastic folds a correct subterm into a larger error, see below).

Not every type gets an error node: names (`Func.t`), strings and records
(the declaration of a predicate, of a macro…) have no room for one. An error
there goes up to the nearest enclosing node that has one.

## 5. Step 2: an error rule in the grammar

Mastic repairs the parse with a special token, `ERROR_TOKEN`, which carries
a `Mastic.Error.t`. For the parser to accept it, the grammar says where an
error may stand: one rule per type that has an error node.

```ocaml
(* parser/grammar.mly *)
%token <Mastic.Error.t> ERROR_TOKEN

decl:          ... | e = ERROR_TOKEN { Program.of_token e }
closed_term:   ... | e = ERROR_TOKEN { Term.of_token e }        (* any term position *)
clause_hd_closed_term: ... | e = ERROR_TOKEN { false, Term.of_token e }
atype_term:    ... | e = ERROR_TOKEN { TypeExpression.of_token e }
fotype_term:   ... | e = ERROR_TOKEN { TypeExpression.of_token e }
kind_term:     ... | e = ERROR_TOKEN { TypeExpression.of_token e }
attribute:     ... | e = ERROR_TOKEN { attribute_of_token e }
```

`closed_term` is enough for terms: every term position (an argument, an
operand, an element of a list, a body) can be a `closed_term`, so an error
can stand anywhere a term can. Adding the rule to `term`, `head_term`… as well
would only create conflicts in the grammar.

These rules add two conflicts to the grammar, both on the same question: at
the beginning of a declaration, is an error token a whole broken declaration,
or the broken head of a clause? Menhir chooses the declaration.

**When Mastic folds the stack into an error.** If an error token does not
fit where it is, Mastic takes the item on top of the parser stack, merges it
into the error, and tries again, until the error fits somewhere. The
function `reduce_as_parse_error` (in `parse.ml`) says how an item of the
stack becomes a piece of an error. Here every item keeps its content: a term
stays a term (`Term.build_token`), a type a type, a list of terms its
elements, a name its text. So an error node does not lose what was parsed
before the error: it contains it.

## 6. Step 3: the recovery strategy

When a token does not fit, Mastic calls the function
`Recovery.handle_unexpected_token` (in `parse.ml`) with a description of the
parser state, and the function chooses one of these actions:

| action | what Mastic does |
|---|---|
| `Reduce p` | completes the rule `p`, as if the token were what follows it |
| `GenerateToken t` | inserts the token `t` before the unexpected one |
| `GenerateHole` | inserts an empty error token: an error node where something is missing |
| `TurnIntoError` | turns the unexpected token into an error token |

The strategy for Elpi uses them as follows. Each rule is shown with what
`main.exe` prints.

**A term or a type is missing: insert a hole.** When the parser waits for a
term (or a type) and gets something else, an empty error node takes the
place of the missing term, and parsing goes on with the token:

```
input: p :- X is + 2 * 3.
error: line 1, column 10: completed with _
ast:   clause (:- p (is X (+ Err«» (* 2 3))))

input: pred q i:.
error: line 1, column 9: completed with _
ast:   pred q (pred i:Err«»)
```

The parser "waits for a term" when the items of its state expect a term or
a type next, and none of them is complete (function `expects_term_or_type`).

**At a `.`, at the end of the file, or at a restart point: finish the
declaration.** A *restart point* is a token that is probably the beginning of
the next declaration: a token at the beginning of a line, or a keyword that
only begins declarations (`pred`, `type`, `kind`, `namespace`, …). There the
current declaration must be finished, by trying in order:

1. reduce, if a rule can be completed;
2. insert the `.` or a closing bracket `)` `]` `}`, if the parser accepts it:

   ```
   input: p X :- q (X, r.
   error: line 1, column 14: completed with )
   ast:   clause (:- (p X) (q (, X r)))
   ```
3. insert a `.` anyway (Menhir may accept it after reductions of empty
   rules, which Mastic does not list);
4. insert a hole, in case a term is missing before the `.`;
5. make the whole declaration an error, with a second error token,
   `DECL_ERROR_TOKEN`, that only `decl` accepts: Mastic folds the stack into
   it up to the declaration.

Thanks to the restart points, an unfinished declaration does not swallow the
next ones:

```
input: typeabbrev xx               (the type is missing)
       namespace foo {
       pred f i:xx.
       }
error: line 2, column 0: completed with _
error: line 2, column 0: completed with .
ast:
  typeabbrev xx                    (its type is a hole)
  namespace foo {
  pred f (pred i:xx)
  }
```

**Otherwise:** reduce inside a term if possible, else turn the token into an
error. At the beginning of a declaration, a token that does not fit is always
turned into an error.

[`STRATEGY.md`](STRATEGY.md) compares this strategy, rule by rule, with the
one of the first version (the PR LPCIC/elpi#385 on Elpi).

## 7. Never crash

An error-resilient parser must never fail. Three things made the Elpi parser
fail on broken programs; they are fixed on the error-resilient path only
(the normal path of Elpi is unchanged):

- **The lexer raised exceptions**: on an unknown character (`$`), an
  unterminated string, quotation `{{` or comment `/*`. It now returns an
  error token. For an unterminated string, the error is just the opening
  `"`, and lexing starts again right after it, so that the rest of the file
  is still read. The lexer records these errors, which are reported with the
  others:

  ```
  input: p 1.
         p $ 2.
  error: unexpected character $ lexical error
  ast:   clause (p 1)
         clause (p Err«$» 2)
         clause (p 3)
  ```
- **The semantic actions of the grammar raised exceptions** on programs that
  are syntactically correct but ill-formed (`bind '\' operator must follow a
  name`, a bad macro, …). They now *defer* the error (`Ast.Term.defer`):
  the action returns an error node, and the error is reported with the
  others.
- **A string whose closing quote is missing** runs to the next `"` in the
  file, maybe far away, and everything in between is lost. When a file has
  errors, it is parsed a second time with strings that cannot span lines, and
  the result with more correct declarations is kept.

## 8. Measuring the recovery

To compare recovery strategies we need a number. The question is: I have a
good program P1 with its tree A1; I damage it into P2, the recovery gives
the tree A2; **how much does A2 look like A1?**

**The nodes.** A tree is seen as the set of its nodes, each written as a
label and a span in the source:

```
p :- X is 1 + 2 * 3.      clause 0-19, app::- 0-19, const:p 0-1, app:is 5-19,
                          const:X 5-6, app:+ 10-19, data:1 10-11, app:* 14-19, …
```

Error nodes are not counted: they stand for "unknown".

**Aligning the two programs.** P1 and P2 differ in one region (the damage):
positions before it are the same, positions after it are shifted by the
difference of length, and positions inside it are unknown, so they match any
position of the damaged region of the other program. This way, the clause
around a damaged term is still expected. Nodes lying entirely in the damaged
region (deleted or inserted text) are not counted: nothing can be expected of
them.

**The two numbers.**

- **recall** = matched nodes / nodes of A1: *how much of the good tree is
  recovered*. An error node loses the nodes it replaces, so a large error
  lowers the recall.
- **precision** = matched nodes / nodes of A2: *how much of the recovered
  tree is right*. An error node does not lower it (it does not pretend to
  know), but a wrong structure does.
- **F1** = 2 × precision × recall / (precision + recall), one number for
  both.

This is the PARSEVAL measure, used to evaluate parsers of natural languages.

**Two examples.** The good program `p X :- q X, r X.` then `p 3.`, damaged
by cutting the end of the first clause:

```
input: p X :- q X,
       p 3.
ast:   clause (:- (p X) (, (q X) (p 3)))
measure: precision 78.6% (11/14) recall 73.3% (11/15) F1 75.9%
```

The parser read `p 3` as the second conjunct of the first clause: a valid
parse, but a wrong one. Precision says it (3 of the 14 nodes are wrong: the
merged conjunction and clause), and recall too (the clause `p 3.` is lost).
With an unterminated string instead (`p "abc".` damaged into `p "abc.`):

```
input: p "abc.
ast:   clause (p Err«"» abc)
measure: precision 91.7% (11/12) recall 91.7% (11/12) F1 91.7%
```

**Where the measure is printed.**

- `cases.t` runs the 32 broken programs of `cases/`, each one against the
  good program it comes from (`cases/*.ref`): `main.exe -ref GOOD FILE`;
- `fuzz.t` fuzzes programs as in `test/` (a character replaced by `;`, a
  space or `$`), and prints the measure of each fuzzed input against the
  original. It also prints `note: not a subterm`, as in `test/`, when the
  fuzzed tree is not included in the original one;
- `recov.py fuzz FILES` simulates editing: for each file, 10 edits of each
  kind (the file cut at a token as while typing, a token, a line or a few
  lines deleted, a closing `)` `]` `}` `.` deleted, a token cut in the middle),
  and it sums the measure over the edits. A crash counts as recovering
  nothing. It also reports the error nodes per edit: covering a whole
  declaration (`decl-errs`) or smaller (`term-errs`), and their size
  (`err-chars`).

## 9. Results

The corpus (`corpus/`, each project with its license and origin): the
programs of Elpi's `tests/sources`, and the Elpi files of hierarchy-builder,
Trocq, Trakt, coq-elpi, math-comp, one_num_type and elpiDiff: 387 files,
about 30 000 lines, 21 493 edits.

|                                      | strategy of error-parser | this strategy |
|--------------------------------------|-------------------------:|--------------:|
| crashes                              | 680                      | **0**         |
| precision                            | 99.7 %                   | 99.7 %        |
| recall                               | 90.4 %                   | **98.6 %**    |
| F1                                   | 94.8 %                   | **99.2 %**    |
| errors covering a whole declaration, per edit | 0.27            | **0.06**      |
| characters inside errors, per edit   | 137                      | **28**        |

The first column (`baseline.txt`) is the strategy of the first version of
this work (the branch error-parser of Elpi, LPCIC/elpi#385: reduce inside a
term, otherwise turn the token into an error; the lexer and the semantic
actions raise), run with the same grammar and error nodes. Both strategies
rarely build a wrong structure, so precision is the same; the difference is
how much of the good structure survives an error. Details per kind of edit
are in `baseline.txt` and `improved.txt`.

## 10. What remains to do

The low scores of `cases.t` show what the strategy does not handle yet:

- a missing `]` before `:-` (`p [X|Y :- q X.`, recall 40 %);
- an extra `)` (`p X :- q X), r.`): the error swallows the terms before it;
- a missing `.` when the next line can continue the clause
  (`p X :- q X,` then `p 3.`): the next clause is read as part of this one;
  only a guess based on indentation could split them.

And some limits of the method:

- the measure aligns the two programs on a single damaged region: with two
  distant errors, everything between them is ignored;
- `accumulate` of a file that cannot be found reads an empty file (only
  parsing is tested here).
