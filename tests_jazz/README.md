# Mastic on the Jasmin grammar

This directory applies Mastic to the parser of
[Jasmin](https://github.com/jasmin-lang/jasmin), a language for
high-assurance cryptographic code, as [`test_elpi`](../test_elpi) does for
Elpi. It shows, step by step, what has to be added to a Menhir parser to
make it error resilient, and it measures how good the result is.

## 1. The problem

A compiler may stop at the first syntax error, an editor cannot: while
someone types, the program is almost never correct, yet the language server
must still highlight it, find definitions, complete names. It needs a parser
that **always returns a syntax tree**, where the broken parts are marked as
errors and the rest is as it would be without the error.

Take the function

```
fn f(reg u64 x) -> reg u64 {
  x = x + * 3;
  return x;
}
```

The left operand of `*` is missing. A good error-resilient parser should
return the tree of `x = x + (Err * 3)`: a hole `Err` where the operand
should be, and the rest of the function parsed normally. That is what this
directory achieves:

```
input: fn f(reg u64 x) -> reg u64 {
         x = x + * 3;
error:           ^    recovered syntax error
         return x;
       }
error: line 2, column 10: completed with _
ast:
  fn f(reg u64 x) -> reg u64
    x = (+ x (* Err«» 3))
    return x
```

Mastic does the hard part: it drives the parser generated by Menhir, and
when a token does not fit, it repairs the parse. The grammar writer provides
three things, the three steps of the [README of Mastic](../README.md), which
are the sections 4 to 6 below.

**The copy of the parser.** `parser.mly`, `lexer.mll`, `syntax.ml`,
`location.ml(i)` and `annotations.ml` are the files of `compiler/src` of
Jasmin. Jasmin's parser depends on a few more modules, which are replaced
by small ones so that the parser builds alone in this dune project (library
`jazz_parser`):

- `wsize.ml` and `warray_.ml`: in Jasmin they are extracted from the
  Rocq proofs; here only the three types the parser uses are written;
- `utils.ml`: Jasmin's `Utils` is built on batteries; only what the lexer
  and `syntax.ml` use is kept (`Hash.of_enum`, `String.count_char`,
  `Option.default`, `pp_list`, …), written with the standard library;
- `annotations.ml`: `BatList.find_map_opt` becomes `List.find_map`.

Then the changes of the steps below: error nodes in `syntax.ml`, error
rules and two error tokens in `parser.mly`, a recovering mode in
`lexer.mll`. The grammar is otherwise unchanged, except one rule: the type
of a global is `loc(ptype_r)` instead of `ptype` (section 5). Menhir is run
with `--canonical` instead of Jasmin's `--strict` (section 6).

The normal path (`Parse.strict`, `main.exe -strict`, which is Jasmin's
`Parser.module_ Lexer.main`) is unchanged: on the 1044 files of the corpus
it gives exactly the same tree as the error-resilient parser, which reports
no error on any of them.

## 3. Trying it

```sh
dune build ./tests_jazz/main.exe
printf 'fn f(reg u64 x) {\n  x = x + ;\n}\n' | ./_build/default/tests_jazz/main.exe   # one program
./_build/default/tests_jazz/main.exe -ref good.jazz bad.jazz        # with the measure
./_build/default/tests_jazz/main.exe -strict good.jazz              # the normal path
dune runtest tests_jazz                                             # the cram tests
python3 tests_jazz/recov.py fuzz $(find tests_jazz/corpus -name '*.jazz')   # the simulation
```

How to read the output of `main.exe`:

```
input: fn f(reg u64 x) -> reg u64 {      the program, line by line
         x = x $ 1;
error:       ^^^^^  recovered syntax error  under a line: the error nodes in it
         return x;
       }
error: invalid char: `$' lexical error
ast:                                      the recovered AST
  fn f(reg u64 x) -> reg u64              one item or instruction per line,
    x = Err«x $ 1»                        blocks indented, expressions as
    return x                              s-expressions: (+ x 1) is x + 1
```

An error node shows the text it covers, `Err«…»`. When the recovery
inserts a token, a line `error: line L, column C: completed with T` says
it (`_` is a hole, an empty error node); with `-ref` or `-fuzz`, a line
`measure: …` gives the measure of section 8.

## 4. Step 1: an error node in every AST type

The parser can only return a tree with errors if the tree can hold them. So
every type of the AST that can be broken gets a constructor for errors,
which carries a `Mastic.Error.t` (the pieces of text and subtrees that were
folded into the error, with their positions):

```ocaml
(* parser/syntax.ml *)
type pexpr_r = PEVar of pident | PEInt of ... | PEOp2 of ... | ...
  | PEError  of Mastic.Error.t                    (* a broken expression *)
and ptype_r = TBool | TInt | TWord of swsize | ...
  | TError of Mastic.Error.t                      (* a broken type *)
type plvalue_r = PLIgnore | PLVar of pident | ...
  | PLError of Mastic.Error.t                     (* a broken left value *)
type pinstr_r = PIAssign of ... | PIIf of ... | PIFor of ... | ...
  | PIError     of Mastic.Error.t                 (* a broken instruction *)
  | PIErrorBlock of Mastic.Error.t * pblock       (* if/for/while with a broken head *)
type pitem = PFundef of pfundef | PParam of pparam | PGlobal of pglobal | ...
  | PError of Mastic.Error.t                      (* a broken item *)
  | PFunError of Mastic.Error.t * pfunbody        (* a function with a broken header *)
```

Each error node is *registered* with Mastic, which tells Mastic how to build
it and how to recognise it. This is the boilerplate of the README of
Mastic, at the end of `syntax.ml`, once per type:

```ocaml
module Expr = struct
  type Mastic.Error.t_ += Expr of pexpr           (* an expression inside an error *)
  let Mastic.Error.Registered { of_token; build_token; _ } =
    Mastic.Error.register "pexpr" {
      Mastic.Error.pp = SPrinter.pp_expr;
      match_ast = (function { L.pl_desc = PEError x; _ } -> Some x | _ -> None);
      match_error = (function Expr x -> Some x | _ -> None);
      build_ast = (fun x -> L.mk_loc (loc_of_error x) (PEError x));
      build_error = (fun x -> Expr x) }
end
```

and the same for `Type`, `Lvalue`, `Instr` and `Item`. `of_token` turns an
error token into an error node (used by the grammar, step 2);
`build_token` turns a correct node into a piece of an error (used when
Mastic folds a correct subtree into a larger error, see below).

Two nodes are not just an error: `PFunError` and `PIErrorBlock` keep the
block that follows the broken part. A function whose header is broken
(`fn f(reg u64 x reg u64 y)`, `fn (reg u64 x)`) keeps its body; a `for`
whose head is broken keeps its block. Without them, the body of a function
would be read as a sequence of items, and lost (section 6).

Not every type gets an error node: names (`pident`), storage classes,
annotations, the records of a function or a parameter have no room for one.
An error there goes up to the nearest enclosing node that has one.

## 5. Step 2: an error rule in the grammar

Mastic repairs the parse with a special token, `ERROR_TOKEN`, which carries
a `Mastic.Error.t`. For the parser to accept it, the grammar says where an
error may stand: one rule per type that has an error node.

```ocaml
(* parser/parser.mly *)
%token <Mastic.Error.t> ERROR_TOKEN
%token <Mastic.Error.t> INSTR_ERROR_TOKEN

pexpr:       ... | e=ERROR_TOKEN { Expr.of_token e }
pexpr_noarr: ... | e=ERROR_TOKEN { Expr.of_token e }
ptype:       ... | e=ERROR_TOKEN { Type.of_token e }
plvalue:     ... | e=ERROR_TOKEN { Lvalue.of_token e }
pinstr_r:    ... | e=ERROR_TOKEN { L.unloc (snd (Instr.of_token e)) }
                 | e=INSTR_ERROR_TOKEN { L.unloc (snd (Instr.of_token e)) }
                 | e=ERROR_TOKEN b=pblock { PIErrorBlock (e, b) }
top:         ... | e=ERROR_TOKEN { Item.of_token e }
                 | e=INSTR_ERROR_TOKEN { Item.of_token e }
                 | annotations call_conv? FN e=ERROR_TOKEN body=pfunbody { PFunError (e, body) }
                 | e=ERROR_TOKEN body=pfunbody { PFunError (e, body) }
```

`pexpr` is enough for expressions: every operand, argument, index,
condition is a `pexpr` (or a `pexpr_noarr` in annotations). The error rule
of instructions is on `pinstr_r`, after the annotations, and not on `pinstr`:
the annotations of an instruction may be empty, and an error token before
them would conflict with the error rule of left values.
`INSTR_ERROR_TOKEN` is an error token that only an instruction (or an
item) accepts: the recovery uses it to make a whole instruction an error
(section 6).

**Conflicts.** The first version of these rules had three shift/reduce
conflicts, all on the same question: at the beginning of an item, is an
error token a broken item, or the broken type of a global (a global begins
with its type, `u64 g = 5;`)? Menhir chose the item, but the conflict did
harm anyway: once the empty annotations of a global were reduced, an error
was read as the type of a global, so a broken item and the next one were
glued together (`global Err«…» x = …`). The type of a global no longer
accepts an error token (`pgd_type=loc(ptype_r)`), and the grammar has no
conflict. A global with a broken type is an item error.

**When Mastic folds the stack into an error.** If an error token does not
fit where it is, Mastic takes the item on top of the parser stack, merges it
into the error, and tries again, until the error fits somewhere. The
function `reduce_as_parse_error` (in `parse.ml`) says how an item of the
stack becomes a piece of an error. Here every item keeps its content: an
expression stays an expression (`Expr.build_token`), a type a type, an
instruction an instruction, the lists of expressions, left values,
instructions and items their elements one by one, and anything else its
source text. So an error node does not lose what was parsed before the
error: it contains it.

```
input:   x = a b c;
ast:     x = Err«a b c»          (the error holds the expression a, then b, then c)
```

## 6. Step 3: the recovery strategy

When a token does not fit, Mastic calls the function
`Recovery.handle_unexpected_token` (in `parse.ml`) with a description of the
parser state, and the function chooses one of these actions:

| action | what Mastic does |
|---|---|
| `Reduce p` | completes the rule `p`, as if the token were what follows it |
| `GenerateToken t` | inserts the token `t` before the unexpected one |
| `GenerateHole` | inserts an empty error token: an error node where something is missing |
| `TurnIntoError` | turns the unexpected token into an error token |

The strategy starts from the one of `test_elpi`. Its rules, in the order
they are tried, each one with what `main.exe` prints (the name in
parentheses is the switch that turns it off, see section 9):

**1. Give up** (`TurnIntoError`) after 10 inserted tokens in a row, and at
the beginning of an item (as in Elpi at the beginning of a declaration).

**2. An expression, a type or a left value is missing: insert a hole**
(`hole`). When no rule can be reduced, nothing has been inserted yet, and
the next symbol of the state, after the symbols that may be empty (the
optional size of an operator, `+32u`), is an expression, a type or a left
value:

```
input:   x = x + * 3;                    input: fn f(reg u64 x) -> reg {
ast:     x = (+ x (* Err«» 3))           ast:   fn f(reg u64 x) -> reg Err«»
```

**3. At the end of the file, or at a token that begins an item: finish the
item** (`eof`, `item`). A token begins an item when it is a keyword that
only begins items (`fn`, `export`, `param`, `require`, `from`, `namespace`,
`exec`, `type`) or when it is at column 0. Finishing tries, in order: reduce;
insert `;`, `)`, `]`, `}` or `{` if the parser accepts it; insert `{` if the
state waits for a block or a function body (`block`); between two
instructions or two items of a namespace, insert `}` (close the block);
insert a hole once; and finally make the current instruction an error
(`INSTR_ERROR_TOKEN`). So a function cut while typing keeps everything:

```
input: fn f(reg u64 x) -> reg u64 {
         x = x + 1;
         if (x > 0) {
           x = 2;
error: line 5, column 0: completed with }
error: line 5, column 0: completed with }
ast:
  fn f(reg u64 x) -> reg u64
    x = (+ x 1)
    if (> x 0)
      x = 2
```

and an unclosed function does not swallow the next items:

```
input: param int N = 4;
       fn f(reg u64 x) -> reg u64 {
         x = x + 1;

       param int M = 8;
error: line 5, column 0: completed with }
ast:
  param int N = 4
  fn f(reg u64 x) -> reg u64
    x = (+ x 1)
  param int M = 8
```

**4. A missing comma between two parameters** (`comma`): after a parameter
of a function, `reg` or `stack` begins the next one. Mastic does not
propose the separator of a list (`acceptable_tokens` leaves it out), so the
`,` is generated here:

```
input: fn f(reg u64 x reg u64 y) -> reg u64 {
error: line 1, column 15: completed with ,
ast:   fn f(reg u64 x, reg u64 y) -> reg u64
```

**5. Between two instructions** (`instrstart`): `return` closes the inner
block it is in (a `return` only ends a function body); any other token that
does not fit becomes an error, which is an instruction error.

**6. At a token that begins an instruction: finish the instruction**
(`instr`). A token begins an instruction when it is the first of its line,
or a keyword that only begins instructions (`if`, `for`, `while`, `assert`,
`ArrayInit`, `return`). Finishing an instruction is as finishing an item,
except that it does not close the block, and that it inserts the `;`
anyway once (Menhir may accept it after the reduction of an empty rule,
which Mastic does not list):

```
input: fn f(reg u64 x) -> reg u64 {        input: fn f(reg u64 x) -> reg u64 {
         x = x + 1                                  if (x > 0)
         x = x * 2;                                   x = 1;
         return x;                                  }
       }                                            return x;
error: line 3, column 2: completed with ;         }
ast:                                       error: line 3, column 4: completed with {
  fn f(reg u64 x) -> reg u64               ast:
    x = (+ x 1)                              fn f(reg u64 x) -> reg u64
    x = (* x 2)                                if (> x 0)
    return x                                     x = 1
                                               return x
```

**7. A `;` or a `}` that does not fit finishes the instruction**
(`close`): `x = (x + 1;` reads `x = (x + 1);`.

**8. A `{` that does not fit** (`lbrace`): reduce, or insert `)` or `]`,
else a hole, which folds what is before the block into an error, after
which the block fits (`PIErrorBlock`, `PFunError`):

```
input:   for = 0 to 4 {
           x += 1;
         }
ast:     Err«for = 0 to 4»
           x += 1
```

**9. Otherwise: as in Elpi.** Reduce inside an expression, else reduce
anything (`reduce`), else turn the token into an error.

Two more changes are not in `handle_unexpected_token`, but the strategy
relies on them:

- **A canonical LR(1) automaton.** With Menhir's default construction, the
  state after an item is shared by the top level and by namespaces, so a
  stray `}` at the top level made the parser reduce the list of *all* the
  items of the file before detecting the error; the error then swallowed the
  whole file. With `--canonical` the error is detected before the reduction.
  The tables are bigger (the generated `parser.ml` is 865 kB) but the
  language and the trees are the same.
- **Consecutive errors are merged** after parsing (items, and instructions
  of a block), as in Elpi.

## 7. Never crash

An error-resilient parser must never fail. The lexer of Jasmin raises an
exception on an unknown character, an unterminated comment, and an
ill-formed escape in a string. In recovering mode (`Lexer.recovering`, set
by `Parse.resilient` only) it returns an error token instead, and records
the error, which is reported with the others:

- an unknown character (and so the opening `"` of an unterminated string) is
  an error token of one character;
- an unterminated comment is an error for its opening `/*`, and lexing
  starts again just after it, so that the rest of the file is still read:

```
input: fn f(reg u64 x) -> reg u64 {
         x = x $ 1;
error:       ^^^^^  recovered syntax error
         x = x * 2; /* to do
error:              ^^^^^^^^ recovered syntax error
         return x;
error: ^^          recovered syntax error
       }
error: invalid char: `$' lexical error
error: unterminated comment lexical error
ast:
  fn f(reg u64 x) -> reg u64
    x = Err«x $ 1»
    x = (* x 2)
    Err«/* to do   »
    return x
```

The semantic actions of the grammar of Jasmin do not raise (the only
`parse_error` is in the `error` rule of Menhir, which Mastic never uses).
On the 59 566 damaged programs of section 9, the parser never crashed.

## 8. Measuring the recovery

The measure is the one of `test_elpi` (see its README for the details):
a tree is seen as the set of its nodes, each a label and a span in the
source; the good program P1 and the damaged one P2 are aligned on their
damaged region; and

- **recall** = matched nodes / nodes of the good tree: *how much of the
  good tree is recovered*;
- **precision** = matched nodes / nodes of the recovered tree (error nodes
  aside): *how much of the recovered tree is right*;
- **F1** = 2 × precision × recall / (precision + recall).

For Jasmin the labels are: `fn:f`, `param:N`, `global:g`, `require`,
`namespace:N`, `typealias:t`, `exec:f` for items; `arg:x`,
`storage:reg`, `return`, `annot:k`; `instr:assign:=`, `instr:if`,
`instr:for:to`, `instr:decl`, …, and `block`; `lv:var:x`, `lv:get:t` for
left values; `type:u64`, `type:u64[]`; `var:x`, `int:3`, `op2:+`,
`op1:!`, `call:f`, `prim:f`, `get:t`, `fetch`, … for expressions.
Parentheses are not nodes. An instruction or function whose head is broken
(`PIErrorBlock`, `PFunError`) is a node without name, which matches
nothing, but its block is there.

Where the measure is printed:

- `cases.t` runs the 32 broken programs of `cases/`, each one against the
  good program it comes from (`main.exe -ref GOOD FILE`);
- `fuzz.t` fuzzes programs as in `test/` (a character replaced by `;`, a
  space or `$`), prints `note: not a subterm` when the fuzzed tree is not
  included in the original one, and the measure;
- `recov.py fuzz FILES` simulates editing: for each file, 10 edits of each
  kind (the file cut at a token as while typing, a token, a line or a few
  lines deleted, a closing `)` `]` `}` or `;` deleted, a token cut in the
  middle), and sums the measure over the edits. A crash counts as
  recovering nothing. It also reports the error nodes per edit: covering a
  whole item (`item-errs`), an instruction (`instr-errs`) or smaller
  (`expr-errs`: expressions, types, left values, headers), and the size of
  the text inside errors (`err-chars`).

## 9. Results

The corpus (`corpus/`, each project with its license and origin): the 1015
`.jazz` files of the jasmin repository that parse (tests, examples), and the
29 files of goldbachJasmin: 1044 files, about 30 000 lines, 59 566 edits.

|                                      | strategy of the Elpi PR | this strategy |
|--------------------------------------|------------------------:|--------------:|
| crashes                              | 14 850                  | **0**         |
| precision                            | 99.26 %                 | **99.41 %**   |
| recall                               | 72.07 %                 | **96.94 %**   |
| F1                                   | 83.51 %                 | **98.16 %**   |
| errors covering a whole item, per edit | 0.29                  | **0.13**      |
| characters inside errors, per edit   | 43.1                    | **12.4**      |

The first column (`baseline.txt`, `JAZZ_BASELINE=1`) is the strategy of the
first version of the Elpi work (LPCIC/elpi#385: reduce inside an
expression, otherwise turn the token into an error; no token is ever
inserted; the lexer raises), run with the same grammar and error nodes.
Most of its crashes are Mastic's "too many loops" at the end of the file:
a file cut inside a function leaves blocks open, and turning the end of
file into an error does not close them (6 882 of the 10 368 truncated
files crash). Details per kind of edit are in `baseline.txt` and
`improved.txt`.

(`JAZZ_OFF=rule1,rule2`); the F1 of the whole corpus without each one (the

still in, at 98.07 %, except for `comma` and `reduce`):

|---|---:|---|

| `instr` (restart at the beginning of a line) | 97.78 % | |

not fit into an error merged with the header. It helps when the header is
really broken, but it also swallows a stray `;` after the header, and the
instruction after it, into the header error.

## 10. What remains to do

The low scores of `cases.t` and the worst edits of the corpus show what
the strategy does not handle yet:

- **a broken function header**: `fn (reg u64 x)` (no name, 58.8 %) or a
  file cut inside the parameters (54.5 %) make the header one error: the
  function keeps its body, but its name, parameters and result types are
  lost;
- **an extra `}`** (`11_extra_close_brace`, 75.7 %) closes the function
  early, and the instructions after it are read as broken items; only a
  guess based on indentation could tell which `}` is too many. The same for
  a deleted `fn …` line: its body is read at the top level and lost;
- **an unclosed namespace** (`31_namespace_unclosed`): the next items are
  read inside it, which is valid; the same for an unclosed block, whose end
  is found at the next `}`;
- **a missing variable**, `reg u64 ;` or `for = 0 to N`: names have no
  error node, so the whole declaration or the head of the loop is an error;
- **a deleted `/*`**: the text of the comment is read as code, which lowers
  precision (and a deleted `*/` makes the comment swallow the code).

And some limits of the method:

- the measure aligns the two programs on a single damaged region: with two
  distant errors, everything between them is ignored;
- `require` is not followed (only parsing is tested);
- the baseline is a strategy for another grammar, not a strategy anybody
  would choose for Jasmin: its crashes say more about Mastic at the end of
  the file than about the strategy.
